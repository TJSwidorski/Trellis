01

The audit

Ten review lenses, merged into five clean-context agents: line-level correctness, Windows/Node platform pitfalls, cross-module contracts, DAG execution semantics, safety-guarantee defeat, reuse, simplification, token efficiency, altitude, and doc-vs-code drift. Nothing from this conversation reached them.

I re-read the source myself for thirteen of the fifteen and confirmed the mechanism in every case. The two marked plausible need one run to settle.

The shape of the result

Almost nothing here is a crash. The dominant failure mode is a guarantee that fails open — a check that cannot run, an error scored as a pass, a halt that reports success. That is the worst possible failure class for this specific system, because Trellis's entire proposition is that you can stop reading the code and trust the gate.

The good news is that the architecture is sound and these are point defects in the enforcement layer, not in the design. The doc-drift sweep came back nearly clean: every documented command and flag exists and behaves as written, every stage artifact promised under sessions/ is both produced and independently verified by the driver, and the Windows .cmd shim fix was generalised properly across spawn sites rather than left as a one-off.

Findings, most severe first

01 A failed commit is reported as a merged node, then the work is deleted CriticalConfirmedkit/lib/worker.mjs:282

MechanismcommitWorktree returns a boolean — worktree.mjs:153 knows it can fail — and nothing reads it.

FailureA checkout with no user.email set, or commit.gpgsign with no key. The node passes its gate, git commit exits 128, and runNode returns {status:"passed"} anyway. runner.mjs:170 merges a branch still pointing at base, so git says "Already up to date." and exits 0. Status is set to merged and removeWorktree(..., --force) destroys the only copy. REPORT.md says green. main has zero lines of it.

FixRead the return value; on false, fail the node. Then assert git merge-base --is-ancestor after every merge — "already up to date" must never count as a successful merge of new work.

02 The gate command can write anywhere on the host CriticalConfirmedkit/lib/gate.mjs:24

MechanismEvery boundary check is git status run with cwd set to the worktree. It reports nothing about paths outside that directory, so denyWrite — which is only ever matched against git-status output and against ### FILE: block paths — never applies to them.

FailureA node legitimately scoped to src/calc.mjs gets an implementation whose top level writes ../../.git/hooks/post-merge. A linked worktree's .git is a file; the real hook directory is the orchestrator repo's. The write shows up in neither changedDuring nor ignoredDuring, tests pass, and runner.mjs:170 runs git merge in the repo root — executing the hook as you. The same route reaches ~/.ssh, .claude/settings.json, and kit/lib/gate.mjs itself.

FixThis is the one finding that cannot be patched with a check, because the gate runs arbitrary project commands by design. It needs a real boundary: run gates in a container or sandbox. references/worker-trust.md already admits "not a sandbox" for the process — the gap is that worktree containment is asserted elsewhere with nothing enforcing it.

03 Any non-zero exit counts as a killed mutant CriticalConfirmedkit/lib/mutate.mjs:110

Mechanismif (r.code === 0) records a survivor; every other exit code silently records survived:false. There is no detectEnvFailure here — and verify.mjs:296 performs exactly that check for the structurally identical situation, with a comment explaining why: a missing dependency makes every test look strong. That reasoning was never carried across.

FailureThe mutator is cfg.tiers[0], the cheapest model in the config. It emits an unbalanced brace or an import that doesn't resolve. The gate exits 1, checked increments, survivors stays empty, and the node merges as MERGED with mutationsChecked: 3 written into state and REPORT.md. A systematically broken mutator produces a permanently clean mutation report — the tests were never shown to detect anything.

04 copyRepo strips node_modules, so the gates it runs cannot work CriticalPlausiblekit/lib/verify.mjs:327

MechanismThe scratch-copy skip set excludes node_modules, and both the null-stub proof and the mutation check run the project's real gate inside that scratch tree.

FailureGate is npx vitest run. In scratch there is no vitest. In verify.mjs, detectEnvFailure catches it and emits an env-failure for every node, so the only practical remedy is to stop running verify-tests — which finding 06 makes painless. In mutate.mjs, which shares copyRepo but has no such detection, the identical failure is scored as every mutant killed (finding 03). One missing directory disables both of the mechanisms that make delegation safe, in opposite directions.

To settleOne run of trellis verify-tests against a project with an npm-installed test runner.

05 An environment-halted run reports success and exits 0 CriticalConfirmedkit/lib/runner.mjs:237

MechanismLaunching stops on budget.check() || (envHalt ? … : null) at line 198. But the end-of-run sweep at line 237 re-derives const breach = budget.check(); without the envHalt term, so the PENDING → BUDGET pass never runs and every untried node stays pending — which rollup counts as neither done nor stuck.

Failure20-node graph, pytest present but a dependency missing. Node 1 halts the run. state.finishedAt is set unconditionally, process.exitCode = stuck ? 1 : 0 gives 0, REPORT.md shows 0/20 landed with no "cut short" banner, and trellis auto advances to triage, triages an empty run, and marks the cycle complete. The one halt path designed to be loud is the only silent one.

06 trellis run never invokes verify-tests CriticalConfirmedkit/bin/cli.mjs:395

MechanismcmdRun calls validateGraph and then run(...). verifyTests is imported at cli.mjs:15 and referenced only by cmdVerifyTests. Nothing in state, the schema, or the runner records whether verification ever happened, or when relative to the last edit of the tests.

FailureA test containing assert.ok(true) passes validateGraph — the file exists, isn't ignored, isn't in write scope, all true. The worker writes an empty function, the gate exits 0, the node merges. If the node declares no mutations, runner.mjs:138 short-circuits the mutation block too, and a fully vacuous node reaches main with no discriminating check of any kind.

ScopeThe auto path is safe: driver.mjs:295 spawns the real verify-tests for stage 04. The hole is the manual path, which is the one QUICKSTART teaches first.

07 denyWrite omits the test configs today's runners actually read HighConfirmedtrellis.config.json

MechanismThe $gate-config comment states the principle exactly right — "a worker that can write package.json decides what npm test runs" — and then enumerates incompletely. Missing: vite.config.*, tsconfig*.json, playwright.config.*, babel.config.*, requirements.txt, pom.xml, build.gradle*, .github/workflows/**.

FailureGate is npx vitest run. With no vitest.config.*, vitest reads vite.config.ts. A worker adds a test.include glob that excludes tests/; vitest exits 0 with "no test files found"; runGate returns {ok:true, kind:"pass"}. The frozen test is untouched, so the tamper checks never fire, and the node merges having run zero assertions. tsconfig path mapping achieves the same thing by redirecting the import.

08 Windows gate timeout orphans the test process and hangs the run HighConfirmedkit/lib/gate.mjs:215

Mechanismshell:true on win32 makes the child cmd.exe /d /s /c "<gate>". child.kill("SIGKILL") maps to TerminateProcess on that one handle; Node does no tree kill on Windows. The grandchild inherits the stdio pipe write handles and survives, and 'close' only fires once the process ends and the streams close.

FailureA worker writes an implementation with an unclosed handle. At timeout, cmd.exe dies and the test runner keeps going. Neither close nor error ever fires, the exec promise never settles, and runner.mjs:225's Promise.race never resolves. trellis run sits silent forever with state frozen at running. The timedOut branch at gate.mjs:105 is dead code on your platform.

09 The same orphan bug in runSession — the only timeout in trellis auto HighConfirmedkit/lib/driver.mjs:614

MechanismThe v2.6.0 fix added shell: IS_WINDOWS at line 598 and left the kill path alone. Same shape as finding 08 — the sibling the generalisation missed.

FailureA stage session wedges. At sessionTimeoutMs, SIGTERM kills cmd.exe; the claude process survives holding both pipes; close never fires; await runSession(...) never returns. No verify, no recordSession, no backoff, no retry — the whole chain hangs with 04_tests — attempt 1/N as its last line. There is also no timedOut flag at all, so even on POSIX the driver cannot tell a timeout from a clean exit.

10 The request timeout is cleared before the response body is read HighConfirmedkit/lib/provider.mjs:63

MechanismclearTimeout(timer) sits one line above const raw = await res.text(). So worker.requestTimeoutMs guards only until response headers arrive.

FailureA provider returns 200 with headers and then stalls. res.text() blocks indefinitely with the abort controller already cancelled. chatWithBackoff can't retry because it never sees a throw; the node never returns; the run hangs with no log line and no budget stop. There's no size cap either, so a runaway streamed body buffers until the process OOMs.

11 git() discards spawn errors, so the dirty-tree guard fails open HighConfirmedkit/lib/worktree.mjs:45

Mechanismgit() builds out: (r.stdout || "").trim() and never inspects r.error. A spawn failure is therefore indistinguishable from clean, empty output.

FailureGit not on PATH, or the 32 MB maxBuffer exceeded, and isClean returns true. runner.mjs:38's guard — the one protecting your uncommitted work from being merged into — passes, and the run merges node branches into a branch holding your changes. The same fault hits changedPaths: past 32 MB of status output it returns [], so the gate tells a model that just wrote a correct implementation "you produced no file changes" and the node burns every tier to exhaustion on a false premise.

12 kit/ is not write-protected, contradicting CONTEXT.md HighConfirmed.claude/hooks/protect-runner.mjs:12

MechanismCONTEXT.md:64 states flatly: "kit/ is write-protected by a hook." The hook imports PROTECTED — ten specific paths — and never imports LOAD_BEARING, which is the list that actually contains kit/lib/ and kit/bin/.

FailureA Write to kit/lib/worker.mjs (which calls screenBlocks), kit/lib/runner.mjs (which holds the merge decision and the mutation gate), kit/lib/graph.mjs, kit/lib/config.mjs or kit/bin/cli.mjs exits 0. Deleting one call in worker.mjs disables the test-freeze, write-scope and output-screening guarantees together, and nothing mechanical objects.

NoteThe design intent behind splitting PROTECTED from LOAD_BEARING is sound and well argued in evolve.mjs. The bug is that the hook enforcing the documented claim uses the narrower list.

13 guard-bash is inert in interactive sessions MediumConfirmed.claude/hooks/guard-bash.mjs:33

Mechanismif (!process.env.TRELLIS_STAGE) process.exit(0);. That variable is set only by driver.mjs:595, i.e. only in driver-spawned stages — and driver.enabled is false by default, so the guarded mode is the minority one. The other two hooks match Read|Edit|Write and read file_path, so neither sees a Bash command.

FailureIn an ordinary interactive session, cat .env, printf '' > .trellis/state.json, sed -i against kit/lib/paths.mjs, and git merge trellis/<high-risk-node> are all uninspected — including the merge that OPERATING.md presents as the one non-negotiable human checkpoint.

NuanceThis is defensible as written — the comment calls it "a second layer, not a sandbox". It's ranked Medium because the documentation presents it as the answer to "why can't the orchestrator just merge it", and in the default configuration it isn't.

14 No re-gate after merge, so the tree is never proven MediumConfirmedkit/lib/runner.mjs:170

MechanismWorktrees snapshot the base branch at creation. mergeNode fires the instant a node passes, with no re-run of its gate against the post-merge base, and no verification pass anywhere in run().

FailureTwo nodes with no dep edge and disjoint file globs both launch under concurrency: 3 and both branch from base at t0. The first merges, changing the signature of a shared exported type. The second was gated at t0 against the old signature, passes, and merges cleanly because the files don't overlap textually. The base branch now holds a combination no gate ever executed. MISSION.md's "nothing merges that was not proven against an oracle" holds per node and fails for the tree.

FixRe-run the level's gates at each level boundary before advancing — the cheapest version of this is one extra gate run per level, not per node.

15 The driver hardcodes .trellis while config makes it configurable MediumConfirmedkit/lib/driver.mjs:317

Mechanismdriver.mjs hardcodes the literal ".trellis" in roughly 25 places. Exactly one function — forgedTriageRuns at line 400 — honours cfg.paths.state. The two disagree.

FailureSet paths.state to anything else and the runner writes to the new path while currentRunId reads the old one, returns null, and every stage that attributes evidence to a run fails. Worse with a stale .trellis/ left over: currentRunId returns a stale id while the anti-forgery check reads the new path, so it either silently disables itself or fails a valid stage as forged.

How Trellis actually works

Think of a construction site, not a chatbot.

Trellis pieceConstruction analogy

One cycle, seven stages

Each stage is a separate session that gets cleared afterwards. That is deliberate: a session that runs out of room mid-task reports success having done a fraction of the work. So anything the next stage needs must be on disk before this one stops.

01_ingestValidateCheck the blueprint. If it's wrong, stop — that's correct, not a failure.
02_sliceCut a batchTake the next ≤25 nodes whose deps are already built.
03_casesEnumerateTurn each node's acceptance criteria into edge cases.
04_testsFreeze testsOne test per case. Everything is red — nothing is built yet.
05_buildRun headlessWorktree, cheap model, screen, gate, retry, escalate, mutate, merge.
06_triageJudgeRead only what's exhausted or high-risk. Ignore the rest.
07_evolveImprovePeriodic. Recurring failure patterns become proposals.

Stage 05 is not a session you drive. It is runner.mjs executing the DAG headless. That absence is the central claim of the whole design.

What stage 05 does per node

Create a worktree off the base branch. Build a prompt — the node's contract, its frozen tests, scoped context. Call the cheapest tier. Screen the output against the node's write scope and the absolute denyWrite boundary. Apply it. Run the gate. On failure, feed back up to 4,000 characters of test output and retry; on exhaustion, escalate cheap → mid → strong. On success, run mutation tests, then merge trellis/<node-id>.

The whole loop stops at exactly one place it refuses to pass: a high-risk node — a one-way door, an auth/payments/secrets surface, an interface with two or more consumers — never merges into your base branch without your eyes on the diff.

The three ideas that make it work

  • The test is the contract. Delegating to a cheap model is only safe because an oracle written before the implementation existed decides what gets accepted.
  • Judgment is rationed; implementation is abundant. Your context is the binding resource, so the design's whole job is keeping implementation out of it. The stated metric is orchestrator tokens per shipped node, trending down.
  • Completion is proven, never claimed. "Done" is a file on disk that the driver checks after the session exits. A model saying it finished is not evidence.

The crown jewel

The test author is a different model family than the implementer. Opus writes tests through Anthropic; workers implement through OpenRouter. A backdoor would have to exist in both, coordinated, to survive. It is the strongest safety property in the design and it costs nothing.

A second one is easy to miss. 2026's dominant long-horizon agent failure is context rot — accuracy falling as context grows — and the standard fix, compaction, has been shown to silently drop governance constraints during the rewrite. Trellis sidesteps both by clearing rather than compacting, and re-deriving state from disk. That is a real architectural advantage over the mainstream agent loop, and it is currently undocumented as such.

Where to dig, in order of payoff

  • kit/lib/runner.mjs — the loop. 264 lines. Read this first; everything else is support.
  • kit/lib/gate.mjs + kit/lib/verify.mjs — what makes delegation safe. Findings 02, 04, 06 and 08 all live here.
  • kit/lib/worker.mjs — prompt assembly. Your token bill lives in buildPrompt.
  • kit/lib/state.mjs + kit/lib/graph.mjs — the DAG and its status machine.
03

Where the next order of magnitude is

Start here: your own benchmark is empty

.bench/REPORT.md has a column for Arm A (plain Claude Code) that is entirely dashes, and section 4 — held-out pass rate, the only quality measure — is blank for both arms. The structure of that report is excellent: it pre-registers its own asymmetries, books graph-authoring cost to neither arm, and refuses to score Trellis on tests Trellis wrote. It is a genuinely honest experimental design with no data in it.

Until it is filled, every item below — and every trellis evolve proposal — is an argument rather than a measurement. This is the single highest-leverage thing you can do, and it costs one run per arm.

Track A — Make green mean something

Prerequisite for everything else. A speed improvement on a system that can report false green just gets you to the wrong place faster.

Make every verifier fail closed

High payoffLow effort

Findings 03, 04, 05 and 11 are one bug wearing four hats: an error that could not be evaluated is scored as a pass. Add detectEnvFailure to mutate.mjs; make git() surface r.error; include the envHalt term in the end-of-run sweep; stop stripping node_modules from the scratch copy (symlink it).

MISSION.md already says it: "a green run against weakened gates is a worse outcome than a red run against honest ones." These are the weakened gates.

Make verify-tests a precondition, not a command

High payoffLow effort

Record a hash of every frozen test file alongside its verification result in state. trellis run refuses to start if any test file's hash has changed since it was last proven non-vacuous. This closes finding 06 and gives you something the system currently cannot answer: "were these specific tests ever proven to have teeth?"

Sandbox the gate

High payoffHigh effort

The gate runs arbitrary project commands with no boundary (finding 02). The ecosystem converged on containers-per-agent for exactly this — Dagger's container-use is the reference implementation. A devcontainer or Docker gate also fixes findings 04 and 08 for free: dependencies are present, and killing a container is a real tree kill.

This is the one finding that a code fix cannot close. It's also what would let you raise concurrency past 3 without worrying about what a worker's code does at import time.

Re-gate at level boundaries

Medium payoffLow effort

Finding 14: per-node oracles never prove the tree. Run the level's gates once against the merged base before advancing to the next level. Zerg — one of the parallel-worktree orchestrators — uses exactly this rule: a level doesn't complete until all its workers pass. One extra gate run per level, not per node.

Add property-based tests to the oracle

High payoffMedium effort

Frozen tests are example-based, which is why worker-trust.md has to argue at length about a worker that sees assert(add(2,3)===5) and writes return 5. Property-based tests are structurally resistant to that: you cannot hardcode your way past a universally quantified invariant. The Property-Generated Solver work reports 23–37% relative pass@1 improvement over example-based TDD for exactly this pairing.

This strengthens the single load-bearing assumption of the entire architecture, and it is additive — stage 03 gains a "what invariant holds for all inputs?" question alongside its case enumeration.

Close the mutation loop instead of just warning

Medium payoffMedium effort

Today, surviving mutants set a weak-tests flag and merge anyway. Feed them back as new cases for stage 03 instead. The MutGen result is the argument: a vanilla prompt plateaus at a 53% mutation score and stays there across four iterations without mutation feedback; with the feedback loop it reaches 89.5%.

Track B — Spend fewer orchestrator tokens

The stated success metric. Your own bench data says exactly where to aim.

02_slice is 53% of your orchestrator cost

From .bench/raw.json: of 7.79M cache-read tokens across the cycle, 4.13M are stage 02 alone — and 29,991 of 38,536 output tokens, 78%. Ingest, cases, tests and triage together are less than half of slice. If you optimise one stage, optimise that one; everything else is rounding.

Second target: the "always-on" tax is 22,921 tokens per session — system prompt, CLAUDE.md, CONTEXT.md, and every activated skill description — paid five times per cycle before any work happens. That is ~115k tokens of pure boot cost, and the number to watch before adding anything to the always list.

Fix the worker prompt's cache prefix

High payoffLow effort

buildPrompt places the mutable "current contents of files you may edit" block before the stable write-scope, gate and output-contract sections, so it invalidates everything after it on every retry. Move it to the end, add cache_control breakpoints, and set a stable session_id per node so OpenRouter's sticky routing returns you to the endpoint holding the warm cache.

A node with 3 attempts across 2 tiers currently retransmits its frozen tests and read-only context 4–6 times at full price. This is the cheapest real win in the codebase.

Stop re-sending what cannot have changed

Medium payoffLow effort

Retries rebuild the full prompt and append a synthetic assistant turn. Frozen tests and read-only reference files never change between attempts — only write-scope files do. Refresh those; leave the rest in the cached prefix.

Make the success metric a number the system prints

High payoffLow effort

"Orchestrator tokens per shipped node" is the declared metric and is computed nowhere. Have trellis status print it and store it per cycle. Without it, trellis evolve has no objective function — it can spot recurring failure codes but cannot tell whether the system is getting cheaper.

Note the two cost figures that already disagree (secondary findings): budget.snapshot().costUsd includes mutation spend and runnerCostUsd does not. Pick one before you start trending it.

Track C — Ship faster than plain Claude Code

Sample in parallel instead of retrying in sequence

High payoffMedium effort

Today a failed node retries serially within a tier, then escalates. But you already have a perfect automated verifier — the gate. That is exactly the setting where drawing k candidates at the cheap tier in parallel and keeping the first that passes beats k sequential repairs, because each sample is an independent draw rather than a conditioned one. Anthropic's own multi-agent finding is the general form: token usage alone explained 80% of performance variance, and parallelism is how you scale tokens without growing a context window.

At current tier pricing, three parallel cheap-tier samples cost less than one strong-tier attempt. The gate makes selection free and objective.

Route on node features, not just tag history

Medium payoffMedium effort

routing.mjs is ledger-driven and inert until 5 observations of a tag/tier pair. Cascade research reports 50–98% cost reduction at matched quality, but the routers that achieve it use per-request difficulty signals, not just historical category rates. You have strong per-node features already: number of dependents, write-scope size, case count, risk tag, whether the node is an interface. Start the ladder at mid for the top decile of those and skip a guaranteed-failing cheap attempt.

Make the decomposition ceiling mechanical

Medium payoffLow effort

CLAUDE.md says two review passes per node is the ceiling and a third means the decomposition is wrong. Nothing records or enforces it. Track the count in state and have a third pass refuse, emitting a re-decompose prompt instead. This is the direct lever on long-horizon reliability: success over t dependent steps is p^t, so bounding t per unit and forcing a split when p is empirically low is the whole game.

Give the graph a live view

Low payoffMedium effort

The rule "if you are reading run.jsonl, stop" exists because watching the run is the most expensive thing you can do with your context. A local TUI or web view reading state.json removes the temptation entirely — this is essentially what Conductor and Vibe Kanban sell, and you already have the state file they'd need.

Track D — What the field says you already got right

Worth knowing so you don't trade it away in a refactor.

  • Agentless workers. The Agentless result — a plain localise/repair/validate pipeline beating agent frameworks on SWE-bench at roughly a tenth the cost — is the strongest external evidence for your worker design. Your workers are single-shot with structured file blocks and no tool loop. Resist adding one.
  • Clearing instead of compacting. The 2026 governance-decay work shows compaction silently dropping safety constraints during summarisation. Your session-per-stage-with-disk-handoff avoids the failure mode entirely.
  • Cross-family test authorship. Nothing else in the ecosystem does this. It is a real and cheap security property, and it should be stated far more prominently than a line in worker-trust.md.
  • The stop-and-say-why default. 01_ingest halting on a bad graph, rather than repairing it, is the discipline that spec-driven frameworks like Spec Kit and OpenSpec are converging toward — and the reason they're displacing looser "vibe coding" loops.

The honest competitive read

Trellis's cost is real and front-loaded: five sessions plus a hand-authored product graph, against one Claude Code session. Its advantage — cheap implementation under an oracle, and a build phase that costs you nothing — is structurally sound but currently unmeasured. The brute-force end of the field (a Ralph-style loop) will out-ship it on small greenfield work; Trellis should win as node count and risk rise, because that is where compounding error and context rot kill the single-session approach.

Track A makes that claim true. The benchmark makes it provable. Everything in Tracks B and C is optimisation on top of a thing you have not yet demonstrated — worth doing, but in that order.

04

Verdict

The architecture is better than its implementation. The layering, the artifact-on-disk discipline, the immutable mission, the split between protected and load-bearing paths, the refusal to let a proposal touch the regression suite, the pre-registered benchmark that books its own asymmetries honestly — that is a level of design care well above what the ecosystem is producing.

The defects cluster in one place and share one shape: enforcement that fails open. Six of the fifteen let something unverified be reported as verified. That is fixable in a focused pass, and none of it requires rethinking the design.

The thing that is genuinely missing is not code. It's the held-out number in section 4 of your own benchmark.
